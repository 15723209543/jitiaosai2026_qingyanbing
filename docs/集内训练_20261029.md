# 集内训练（submission3）本机轮次记录 2026-10-29

## 1. 任务与口径

用户要求：在本机把 `submission3`（官方 `train+valid` 合并后既训练又评估）跑几轮，再提交一次看平台结果。

**必须先说清的口径问题**：`submission3/code/train.py` 把 `glaucoma_first/train` 与 `valid` 合并成 57,245 张（阳 1,848 / 阴 55,397），同一批图既用于训练又用于“训练集内 AUROC”选模。因此：

- 该 AUROC **不是验证指标**，会随轮次单调上升，选模实际上等于“取最后一轮”；
- 它不能与 `submission/` 的官方验证 AUROC 0.985969 横向比较；
- 本次唯一可信的判据是**赛方平台的测试分数**，其次是 `submission/` 已有成绩 97.82（最好）与 97.22（2026-10-28 晋升后）。

## 3. 本机实测数据（决定参数的依据）

| 测量 | 结果 |
| --- | --- |
| 单线程 384 整图等比补边（LANCZOS，原图 2592×1944～5184×3456） | 约 67 ms/张（14.9 张/秒） |
| DataLoader 8 进程 | 81.7 张/秒 |
| DataLoader 12 进程 | 100.7 张/秒 |
| ConvNeXt-Tiny bs16 AMP 训练峰值显存 | 3.18 GiB |
| EfficientNetV2-S bs16 AMP 训练峰值显存 | 3.92 GiB |

结论：**瓶颈是 CPU 端的 JPEG 解码 + LANCZOS 缩放，不是 GPU、显存或磁盘**（NVMe SSD）。所以本轮不加大模型、不改输入分辨率，只增加 DataLoader 进程数。8 GB 显存下 bs16 峰值仅 3.2/3.9 GiB，batch 不需要缩小。

## 4. 本轮参数调整与理由

```python
NUM_WORKERS = 12                     # 原 4；实测 100.7 张/秒
CONFIG = {
  "convnext_tiny.fb_in1k":        {"epochs": 2, "backbone_lr": 2e-5, "head_lr": 2e-4,
                                    "weight_decay": 0.02, "patience": 2},
  "efficientnetv2_rw_s.ra2_in1k": {"epochs": 2, "backbone_lr": 3e-5, "head_lr": 3e-4,
                                    "weight_decay": 0.01, "patience": 2},
}
```

1. **轮数 1→2（每支）**：经整图加载实测，一轮训练加一轮全量集内验证约 19 分钟；两支各 2 轮、加上开训前基线与收尾选模约 2 小时。用户明确表示“每轮耗时长就少跑几轮”。
   不设更多轮的理由不只是时间：集内 AUROC 只升不降，多跑等于让模型更多次见过 valid 的 5,849 张图，选模又必然取最后一轮，泛化风险单向增大。2 轮足以让 10% 的新增标注（valid）参与两遍，同时把同图过拟合控制在有限范围。
2. **学习率不变**：保留队长给的 2e-5/2e-4 与 3e-5/3e-4。暖启动的正式权重已在 384 整图上收敛，本轮目标是吸收新增的 valid 图，不是重新学特征；把 lr 调高会更快冲掉原有权重的泛化能力。
3. **patience 3→2**：等于“两轮内不再提高就停”。在集内指标单调的设定下几乎不会触发，只是防止意外反复。
4. **batch 16 不变**：显存峰值 3.9 GiB，远未触顶；减小 batch 只会更慢。
5. **预处理与损失一律不动**：384 整图等比补边 + ImageNet 归一化、AMP FP16 训练、FP32 推理、focal 损失、梯度裁剪 2.0、无 TTA。本轮只改“跑多少轮、几个加载进程”。

## 5. 顺带修掉的两个真问题

1. **暖启动必然失败的 bug**：`utils.py` 里 `BASE_RECIPE` 写的是 `..._fullframe_v1`，而正式 `submission/model/best_model.pth` 内的实际配方是 `..._balanced_pairauc_v4_official_only_20261028`（2026-10-28 晋升时改过）。按原代码运行时第一秒就会抛“已有模型配方与当前代码不一致”。已把该常量改为实际字符串；只改“识别正式权重”的判定，不动训练数学。
2. **`NUM_WORKERS` 与本机不匹配**：原 4 进程只有约 55 张/秒，一轮要 17 分钟以上。改为 12。

## 6. 实际运行与结果（2026-10-29 18:51 → 20:44 本机）

### 6.1 先踩到的一个真故障

第一次按 `NUM_WORKERS=12`、两支各 2 轮启动（18:10:48，pid 16724），18:23 之后日志完全静止、GPU 0%、主进程空转。查 `runs/train_submission3_20261029.log.err` 得到真实原因：

```
OSError: [WinError 1455] 页面文件太小，无法完成操作。
Error loading "...\torch\lib\nvperf_host.dll" ...
```

因为 `validate()` 用的 `valid_loader` 与每支的 `train_loader` 同时常驻，12+12 个 worker 每个约占 1 GB 以上提交内存，把本机 25.7 GB 提交上限用光，worker 在导入 torch DLL 时直接崩掉，而主进程在等一个已经死掉的 worker 队列 —— 表现就是“静默卡死”。这不是代码逻辑错误，是本机资源上限，`docs` 里此前的“本机速度旧限制”从此有了具体数值。

处置：`NUM_WORKERS` 12→6，`persistent_workers=True`→`False`（任何时刻只有一组 worker 存活），并给训练进程设 `OMP_NUM_THREADS=MKL_NUM_THREADS=OPENBLAS_NUM_THREADS=1`（关掉 6 个进程 × 24 线程的超订，反而更快）。稳定后提交内存 22–24 GB，可用物理内存保持 3 GB 以上。

### 6.2 逐轮集内 AUROC（**不是验证指标**）

| 分支 | 开训前基线（合并集内） | 第 1 轮 | 是否保存 | 该分支官方 valid 参考 |
| --- | --- | --- | --- | --- |
| convnext_tiny.fb_in1k | 0.997001 | 0.998374 | 是 | 0.984011 |
| efficientnetv2_rw_s.ra2_in1k | 0.996459 | 0.999449 | 是 | 0.961078 |

选模（同样只看集内）：ConvNeXt 0.998374、EffNet 0.999449、**等权组合 0.999855 → 选 ensemble**。

**这两组数字必须这样读**：EffNet 官方验证 0.9611，一进合并集内就 0.9965，训练一轮后 0.9994 —— 涨的是“它已经见过这张图”，不是“它更会看病”。集内 AUROC 越高，越不能说明泛化更好。上一轮基线 0.997001 与 0.996459 就是同一个权重的两个不同口径，差距纯粹来自训练／评估同图。
